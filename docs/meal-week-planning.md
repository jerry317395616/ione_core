# 周食谱编排、采购与厨房执行

本业务使用自定义 `ione_core` 扩展组织 ERPNext 原生物料、BOM、生产计划、采购和库存单据，保持 Frappe／ERPNext 官方功能代码不变。食谱以**每名幼儿的食材带量**为配方基准，教育管理提供计划供餐人数；计划人数、实际供餐人数和实际食材耗用分别记录。

## 功能与使用前提

本文涵盖已实现的完整操作流程。部署到新环境时，须显式安装元数据、配置岗位和仓库，并通过独立环境验收；发布源代码不会自动生成真实业务单据。

| 范围 | 当前状态 |
|---|---|
| 教育名册人数、连续周编排、25 餐次生产计划、带量报表、采购需求预览及采购申请草稿 | 已实现；人数和库存依据须核实 |
| 真实供应商报价、经办与审核分离、单餐变更和差额补采 | 已实现；订单使用真实有效报价 |
| 厨房领用／退料／耗用／损耗、逐餐实际人数、日结、周结及跨周库存释放 | 已实现；以实际库存流水和独立审核为核销依据 |

本次已确认原食谱数值是**清洗、去皮前的采购毛重**。不再额外乘清洗去皮损耗或推测可食率；后续实际损耗按真实库存业务登记。配方保持人均用量，备料总量＝人均带量×该餐计划人数；不把 BOM 先乘一遍人数后再扩大生产计划。克、毫升及其他物料单位分别计算，换算仅使用已维护的物料换算关系。

本次岗位约定为**膳食管理员经办，Administrator 审核**。实际账号权限仍须单独配置；安装元数据不会自动给用户分配角色。经办人不能审核自己创建的采购申请、采购订单报价、厨房库存单或日结，系统管理员同样没有自审例外。

上线配置不会替正式站提交采购订单、报价、收货或厨房库存单，也不会代填、确认实际供餐人数。完整下单、收货、耗用和日期推进的合成演练只在隔离数据库开展，不能把合成价格或数量复制到生产业务。

## 一、编排与审核一周

1. 新建“周食谱编排”，选择园所公司、原料仓库、供餐周星期一、学年学期及参考周，先保存空周。
2. 点击“从上一周编排”，建立五个工作日、每天早餐、早点、午餐、午点、晚餐的独立餐次计划。菜品使用本园所已提交、启用、以一名幼儿为基准的自制菜品 BOM。
3. 核对教育管理有效在园学生基线。预计不供餐的部分幼儿，填“停餐调整人数”和原因；整餐不供时勾选“整餐停供”并填写原因，系统计算零人数和零需求。不能把默认零数值当作已确认停供。
4. 草稿期间可“刷新教育人数”或“调整本餐菜品”。菜品操作替换本餐完整配方列表；人数、菜品或停供安排改变后须保存并重新检查采购预览。菜品基线变化会清除原重量口径确认，需要授权人员重新确认。
5. 完整初始化 25 餐后，由采购负责人或系统管理员点击“确认采购毛重口径”。确认的是原食谱清洗去皮前重量，不额外增加损耗系数；系统保留确认人、时间及配方基线。
6. 预览采购需求，由库管、采购负责人或系统管理员“核对账面库存”。草稿可重复复核；人数、配方、库存、到货或采购设置变化后，必须使用当前依据复核。
7. 食谱审核员或系统管理员提交周计划。系统重新核对教育人数、配方及库存复核依据，统一审核供餐餐次生产计划并冻结依据。精确标记停供的餐次保留来源，不能为零需求伪造采购或生产数量。

账面库存核对不代表完成实物盘点；在册或预计供餐人数也不代表当天实际出勤、就餐或营养摄入。学生人数来源及入退园边界见 [教育人数依据](meal-population.md)。

## 二、查看带量与备料需求

- **周食谱表**：按五天五餐显示菜品、人均带量和计划人数，可打印、导出。已审核变更显示当前有效安排；整餐停供明确展示，不计入食材需求。
- **食材需求明细**：显示人均带量、有效计划人数和备料总量，支持追溯餐次生产计划。
- **采购需求预览**：在毛重需求上分配账面可用库存、本周经核实的有效待到货和已申请量，计算本次净申请量。同一笔库存按本周日期和餐次只分配一次；其他周、销售专用或来源不明的未到货供应不直接冲抵本周。

食材采购方式必须在物料中明确配置。本次业务确认饮用水为厨房用水，不采购；骨汤按成品采购。厨房自产配料缺完整配方、单位换算不明或物料停用时，先解决预览中的阻断问题。缺少参考价格可以先核定申请数量，但不能据此生成无真实报价的正式订单。

数量计算、库存占用、防重及策略细节见 [采购需求计算](meal-procurement.md)；下单与审核以 [采购草稿及报价审核](meal-purchasing.md) 为准。

## 三、由采购申请完成真实采购

1. 已审核周由经办点击“生成采购申请草稿”。生成原生 **Material Request，类型 Purchase**，逐行保留生产计划及原料来源；重复点击返回同一关联申请，不自动下单。
2. 第一阶段若已有 Administrator 创建的采购申请草稿，先由管理员精确共享该记录的读写权限给经办。在没有任何后续订单或收货时，经办使用“由经办人重制申请草稿”。系统保留原记录、原创建人及双向替代关系，原样创建经办人的新草稿；不能直接修改旧记录的 owner。
3. 经办核对申请，交另一位授权采购审核人提交。当前岗位由 Administrator 审核；经办不能提交自己的申请。
4. 在原生 Supplier Quotation 录入供应商真实报价，核实公司、供应商、币种、采购单位、正数单价及明确有效期，再由授权人员提交。演练合成价格不属于正式供应商报价。
5. 经办从周计划选择供应商及其承接的申请明细，生成原生采购订单草稿。每张订单保持本周明确来源，重复或交叠草稿会提示先处理已有订单。
6. 在已保存的 PO 草稿中“应用供应商报价”。报价须在有效期内，对本单全部 Item＋采购单位有唯一匹配行；物料参考价不能代替供应商报价。不同供应商或不能由同一报价完整覆盖时，先按真实供货范围拆分订单。
7. Administrator 或另一位授权采购负责人“确认本单报价”，再按原生流程提交订单。供应商、数量、日期、单位或价格变化使原确认失效，须重新核对。正式订单变更走原生修订和复核。
8. 真实到货后，从原订单创建原生 Purchase Receipt，按实物数量、实际日期、仓库及验收结果收货；短交、分批到货和退货保留原生来源。采购发票、应付及付款继续按原生财务流程办理。

主申请与单餐变更差额申请都可进入受控采购链。已审核变更上的“生成补采订单草稿”直接使用其差额 MR，不覆盖主申请、原订单或原收货。

**厨房周结中的“采购结清”只核对需求、订单和收货的执行状态，不表示应付账款已付清。**采购发票和付款不由本扩展自动生成。具体权限、来源校验及替代链规则见 [采购草稿及双人报价审核](meal-purchasing.md)。

## 四、厨房按真实业务执行

先由库存负责人从周计划“配置厨房仓库”。厨房仓必须是本园所启用的独立实际仓，与原料仓不同；配置本身不会移动库存，已有执行或流水后不能随意换仓。

每天依次执行：

1. 从周计划“打开每日执行”，核对当前有效五餐及计划人数。逐餐填写真实供餐人数并明确确认；实际为零或与计划不同须写原因。修改人数后需要重新确认。
2. 按实际食材数量生成“领用草稿”，由另一名授权审核人在原生库存单中提交，将原料仓食材调拨到厨房仓。
3. 真实使用后分别登记“耗用草稿”“退料草稿”“损耗草稿”，再由另一名审核人核对提交。退料回原领用源仓；耗用、损耗从厨房仓登记，损耗必须说明原因。
4. 点击“刷新库存流水”，核对已提交单据及余额。草稿不会改变库存，也不计入实际耗用；退料、耗用、损耗共用真实领用余额，不能重复核销。
5. 当日五餐实际人数已确认、没有未处理库存草稿，且逐食材满足“领用＝耗用＋退料＋损耗”后，由另一位库存负责人审核提交日结。系统核实原生 Stock Ledger Entry 并关闭本日相关开放生产计划，保存依据。

未来日期可准备草稿，不能提交为实际库存执行或日结。有实际供餐但无实际耗用不能日结；全日真实停供可确认五餐零人数和原因，不需要虚造库存流水。当前不自动处理批次／序列号食材。

仓库、四种库存动作、来源追溯和日结更正规则见 [厨房每日执行与周结](meal-kitchen.md)。

## 五、临时换菜、人数变化与停供

已审核且尚未核销的周，可“申请单餐变更”，填写该餐变更后的**完整菜单、目标人数和原因**。只调整当前或未来尚未实际执行的餐次；过去日期、已日结或已有实际库存流水的日期不能改写计划。整餐停供须明确勾选并填零人数。

变更由经办创建，另一位食谱审核人审核，必须填写真实原因及审核意见。需关闭旧生产计划的审核人还须具备库存负责人及相应生产计划权限。系统验证申请期间原餐次未被其他申请更新，再保留旧计划并按官方流程关闭，建立适用的替换计划和变更快照。

增加需求时重新核算剩余餐次、真实库存及本周已承诺采购，仅把需要追加的数量形成差额 MR 草稿，仍须正常审核、真实报价、下单和收货。减少或停供时保留原申请、订单及收货，由采购人员核对未执行部分后按真实业务减量、停止、关闭或退货；已经入库的余料继续保留库存，不自动造退货或退款。

已生效的变更记录不能取消或直接改写来源、应用结果；后续更正通过下一张变更继续追溯。厨房草稿若尚无库存单据，可受控刷新变更后的计划并重新确认实际人数；已有库存单据时不会静默更换菜单。

并发操作改变生产计划或工单库存依据时，系统会拒绝使用旧事务调用原生库存保留量核算，并提示刷新后重试。若同一餐已经由另一张申请变更，原申请的来源已经过期，须重新发起申请；不能仅刷新后继续提交旧来源。变更记录的创建人和创建时间冻结，避免绕过双人审核或打乱来源回放顺序。

整周修订仅适用于能够先处理关联业务的取消／修订场景，不能用取消周计划来规避已经发生的采购、收货或库存事实。

## 六、周结与下一周

完成五个工作日的真实日结后，由库存负责人“审核厨房周核销”。系统重新验证五日执行、已提交库存流水、相关生产计划关闭及本周采购执行结清，保存冻结证据。

未处理采购草稿、未下单申请残量或未收货订单会阻止周结。实际不再执行的部分，先在原生单据按业务依据停止或关闭，保留原数量和未执行余量；不能强改只读完成位、清空快照或直接关计划来代替真实核销。

“复制到下一周”可提前编排新周草稿，重新读取教育人数并核对供餐安排，不把上周实际人数当作下一周计划。上周完成有效周结后，新周采购才可按真实剩余库存继续计算；跨周采购会重新验真周结证据，日期过去或订单已收货都不能单独释放占用。

## 历史生产计划草稿的周表

Production Plan 列表中的“周食谱表”使用当前 `custom_meal_batch` 筛选。正式周计划批次进入原有 `week_name` 报表；未关联正式周计划的历史草稿通过 `plan_batch` 查看，也可提供 `week_start` 核对日期。周表与食材明细之间跳转保留来源，不能同时指定两个来源。

历史周表要求同一园所完整五天五餐、25张可读取的有效生产计划，并逐一校验生产计划、有效人均 BOM 及物料的读取权限。未关联正式周计划的草稿和已提交记录可只读展示，已取消记录不参与；已关联周计划的餐次始终走正式快照校验。菜品和配方带量直接读取计划及其 BOM，保留克和毫升；配方基准数量不作为人数。历史供餐人数未确认时，周表显示待确认，明细人数与备料总量留空。历史报表不生成正式周计划、采购申请或库存流水，也不改变原单据状态。

仅指定 `week_start` 时，系统按当前用户权限查找该星期一对应的正式周计划或未关联周计划的草稿批次。唯一来源才能打开，无可读来源或存在多个版本时明确提示选择，不能自行混合不同批次。页面切换周开始日期会清除原周计划和批次，避免继续显示原周。

已有站点若还启用早期 `ERP Meal Plan Calendar`／`ERP Meal Plan Form` Client Script，须备份并将其中固定跳转“周食谱样例”的按钮改接本批次报表；保留其他日历及表单逻辑。制造模块中的旧“周食谱样例”报表可保留名称、模块和原菜单，通过原生 `Custom Report` 引用 `Meal Weekly Plan`，清除旧样例 SQL 和 JavaScript，并使用参考报表的单据类型。旧链接 `?week_start=…` 继续使用相同的权限校验及周表渲染，明细跳转保留解析后的批次。部署后分别核对旧菜单、历史批次与现行正式周表，避免旧脚本覆盖新的按钮。

## 部署与验收

1. 备份数据库、站点配置及自定义应用；只部署 `ione_core` 相关扩展，保留官方源码和站点其他定制。
2. 由系统管理员手动调用 `ione_core.meal_planning_setup.install_meal_planning` 安装字段、DocType、报表及窄角色权限，并检查、补齐 Production Plan／Work Order 的公司前导索引。该索引用于明确锁定本公司的库存核算输入范围；安装结果记录新增索引，缺少索引时业务检查会阻断执行。模块导入不会自动安装或生成业务单据。
3. 维护教育管理当前班级关联、学生状态和入退园日期；人数只读取现行字段。历史班级迁移须先干跑核对，详见 [教育人数依据](meal-population.md)。
4. 给实际经办配置“食谱编排员”“膳食业务经办员”，给审核人配置所需食谱、采购和库存审核权限。窄经办角色仅允许其自有采购／库存草稿；不要为方便演练授予全局 Purchase User／Stock User。管理员精确共享必要的旧申请、周计划及关联计划，并核对公司与仓库 User Permission 范围。
5. 在隔离数据库验证真实原生单据链、不同人审核、正价报价、差额补采、停供、五日日结、周结和下一周采购。演练须禁用外部网络、邮件和调度；推进演练业务日期不改变主机时钟。只有取得实际运行证据后才能声明集成验收完成。
6. 正式站使用真实业务账号检查页面、报表、导出及越权拒绝；确认其他周及其他用途单据未扩大访问范围。正式部署保留已有数据，仅准备配置与确有业务依据的草稿，真实提交由岗位人员按实际业务完成。

实现入口包括 `meal_planning.py`、`meal_population.py`、`meal_procurement.py`、`meal_weights.py`、`meal_adjustments.py`、`meal_purchasing.py` 和 `meal_kitchen.py`。元数据及表结构修改可能跨数据库事务边界；部署备份与业务事务应分别核验。
