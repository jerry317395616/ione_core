# 厨房每日执行与周结

厨房使用原生 Stock Entry 记录实际库存业务，不把食谱需求自动记为实际耗用，也不生成虚构的成品制造记录。计划食材沿用食谱确认的毛重和库存单位，不另乘可食率。

## 经办和审核

- “膳食业务经办员”录入厨房草稿、实际人数和实际食材数量；原生库存单据只有自己的草稿创建、读写权限。
- Stock Manager 或 System Manager 负责审核出入库、日结及周结，并须具备关联原生生产计划的写权限。
- 原生厨房库存单据和日结的审核人与经办人必须不同，系统管理员也没有自批例外。食谱审核员如需批准会关闭旧生产计划的单餐变更，还需要库存负责人及关联生产计划的相应联合权限。

## 仓库和每日操作

1. 库存负责人从周计划配置厨房仓。源仓由周计划决定；厨房仓必须是本公司启用的独立实际仓，不能与源仓相同。配置不移动任何库存。同仓重复配置返回已有结果；已有厨房执行或库存单据后不能改周仓。
2. 从周计划选择工作日建立厨房执行记录，核对当前有效菜单和五餐计划人数。已审核单餐变更或停供会反映到计划来源。
3. 逐餐填写实际供餐人数并明确勾选确认。默认零不表示停供；零人数或与计划不一致须填写原因。
4. 按本次真实数量生成库存草稿，由另一名授权审核人核对后提交原生单据。未来业务可先准备草稿，但不能提交为实际库存业务。

| 厨房动作 | 原生库存单据 | 仓库变化 |
|---|---|---|
| 领用 | Material Transfer | 原料源仓 → 厨房仓 |
| 退料 | Material Transfer | 厨房仓 → 原领用源仓 |
| 耗用 | Material Issue | 从厨房仓登记实际耗用 |
| 损耗 | Material Issue | 从厨房仓登记真实损耗，并说明原因 |

退料、耗用和损耗按本日已提交领用或上日已审核留存的原始领用来源行分配。来源可以属于以前日期和周，但跨所有日期、所有周的实际使用合计不能超过原领用量。损耗与正常耗用共同使用一个余额，不能把已经耗用的食材再损耗一次。单位固定为物料库存单位，不允许前端指定其他仓库、换算或来源。隔夜退料回该领用最初的原料仓，不能改成当前周选择的另一源仓。

同动作已有相同数量的草稿时返回原草稿；数量不同则要求先处理原草稿。草稿不代表实际执行，也不抵扣领用余额。当前不自动处理批次或序列号食材。

## 日结和更正

日结需要五餐实际人数明确确认、无未处理库存草稿，并满足：

**实际期初＋本日领用＝实际耗用＋退料＋损耗＋期末留厨。**

余料可以原地留厨房，无须为日结搬回原料仓。正数期末须逐食材输入真实盘点数量并说明留存原因，由系统与来源余额核对；页面不把账面数预填成实盘。差异必须先核对并按真实业务更正，不能确认不相等的数值，也不能用假耗用、假退料清零。零期末兼容原日结流程，不强制另点留存确认。

实盘确认与当日人数、说明、库存流水及期初来源签名绑定，之后相关数据改变需要重新确认。留存确认人与日结审核人必须不同。`carry_confirmed` 是受控 API 结果，直接修改勾选位或只读快照不能代替盘点和核销依据。

系统逐行验证已提交原生单据及 Stock Ledger Entry，不能仅凭只读汇总或手工勾选完成日结。有供餐人数却没有实际耗用时会阻止日结；全日真实停供可用五餐零人数及原因确认，不必创建假的库存流水。未来日期不能日结。

后日从同公司、同厨房最近一个已审核日结继承期初，保留最初的原生领用行。前日已发生实际业务却未日结时，不能跨过使用其余额；后日已有实际流水或日结后，也不能回填旧日期。期初余料即使不在今天菜单中仍显示在流水中，可真实退料或登记损耗；只有当前菜单物料可新增领用或登记供餐耗用。

日结按该日截止冻结期初、当日流水和逐来源期末。后日合法用料只减少当前可用余额，不改变前日已冻结事实。星期五余料可继续留厨房，下一周承接只转移可追溯台账归属，不新造移库、制造或盘盈。这里的余料是原料食材库存，不新增熟食成品库存业务。

审核通过后，系统通过官方生产计划关闭流程释放本日全部有效原计划、替换计划的库存保留量，保留采购来源及日结证据。精确识别的初始停供配方草稿没有保留量，保持草稿，不伪造提交或关闭。

无库存单据的厨房草稿遇到菜单变更时可受控刷新，原实际人数及留存确认会作废，须重新核对。已有库存单据的草稿不会静默换菜单。已日结的实际人数、审批和核销依据冻结；已纳入周结或有后日承接的记录不能直接取消。有后续退料、耗用、损耗或其草稿引用的原领用也不能直接取消。更正按真实依赖从后向前处理，系统不自动制造反向库存单。

## 周结与下一周

周结要求本周五个工作日均已完成真实日结，所有关联开放生产计划已通过官方流程关闭，且采购来源通过结清检查。未处理采购草稿、未下单申请或未收货订单会阻止周结；原生人工停止、关闭的来源按其证明保留剩余量。

周结保存五日执行、实际库存流水、关闭计划、采购结清和厨房留存来源的冻结证据，状态为“已核销”。有经实盘确认且来源完整的厨房余料不妨碍周结；后周合法使用不会破坏旧周截止证明。清空快照、修改只读完成位或直接关闭生产计划都不能代替周结。

下周提前采购与旧周周结是两件事：采购按各周已认领的原料库存、真实到货和未执行承诺独立核算，不能挪用另一周归属或把厨房余料又算作原料仓共享库存。厨房原料真实领用提交前接入库存归属核对，受控保存原料归属快照；普通表单不能伪造或改写该快照。

## 维护入口

`ione_core/meal_kitchen.py` 提供受控配置、每日记录、库存草稿及周结 API。`confirm_kitchen_carry(day_name, physical_counts, notes=None)` 的实盘输入为 `[{item_code, qty}]`，完整覆盖正期末食材；不能传空值代替实盘。`get_kitchen_ledger` 返回 `opening_qty`、`carry_out_qty`，保留 `balance_qty` 为期末兼容键，并提供按物料允许的动作。

原生 Stock Entry 须接入 `validate_stock_entry` 和 `before_cancel_stock_entry`，并覆盖提交后更新事件；每日执行控制器须委托校验、提交、取消及提交后更新保护。库存归属范围使用公司事务锁，来源余额及跨日使用量使用当前读复核，不在旧 RR 快照中放行超耗。缺少库存归属模块或字段配置时应阻断，不跳过校验。

`verify_week_kitchen_reconciled(week, lock=True)` 是内部验真函数，不写业务数据；正式库存决策使用当前读锁，纯只读审计可传 `lock=False`。它重新检查历史日账、原生流水及采购结清，不只读取周结标志，也不再次请求实时原料可用量而造成递归。`get_kitchen_carry_available` 内部返回可追溯当前余料，采购方不能重复抵扣。

所有提交、库存及完整采购集成测试应先在隔离库进行；合成演练数量与价格不能写入正式站。
